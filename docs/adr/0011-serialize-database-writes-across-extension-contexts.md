# ADR 0011：跨扩展上下文串行写入资料库

状态：已采纳

## 背景

资料库保存在 `chrome.storage.local` 的 `futurecontext.v1` 下。popup、扩展标签页、后台 Service Worker 和投递页面都会修改同一份数据。

原有 `revision` 校验采用「读取 → 检查 → 写入」，不是原子比较并交换。两个调用可能同时通过检查、都返回成功，但后一个写入覆盖前一个。编辑器逐次输入保存草稿，紧接着正式保存时还可能被旧草稿写回覆盖。问题见 [issue #7](https://github.com/star-736/Prompt-Plugin/issues/7)。

## 决策

- `saveDatabase()` 和 `applyDatabaseChange()` 都申请同一个独占 Web Lock：`futurecontext.v1:write`。读取最新资料库、执行 mutator、检查 revision 和写入均在锁内进行。内部保存函数不再重复申请锁，避免嵌套死锁。
- Web Locks 在扩展同源的页面和 worker 之间协调写入，无需把 popup 保存转发给后台，也无需新增扩展权限。上下文终止后由浏览器清理锁。[Web Locks 规范](https://www.w3.org/TR/web-locks/)
- 保留 revision 校验和冲突重试，以拒绝过期的完整快照，并兼容未遵守锁协议的写入。应用内部修改必须通过以上两个入口，mutator 不得嵌套调用它们。
- 等待锁超过 10 秒会取消尚未开始的请求，并报告「尚未开始保存」。取得锁后取消计时，直到真实写入完成才释放锁；不使用 `Promise.race()` 将仍在执行的写入判定为失败。
- 实际扩展环境缺少 Web Locks 时拒绝写入并提示升级浏览器。注入的非扩展 storage adapter 使用模块内的 Promise 队列；该回退不提供跨浏览器上下文的保证。
- `applyDatabaseChange()` 的同步 `onSaved` 回调提供已确认的资料库快照，包含保存后的 revision。popup 据此更新状态，避免保存完成后的额外读取失败被当作保存失败。回调只用于更新内存状态，不执行异步写入或抛出异常。

## 编辑器行为

每个编辑器会话最多保留一个正在执行的草稿任务和一份最新待写草稿。草稿失败被捕获，在表单内持续提示，当前输入保留。

正式保存捕获当前输入、停止待写草稿、等待正在执行的草稿任务，然后保存资产并清除草稿。保存期间禁用编辑和重复提交；放弃编辑也等待已有任务结束，再清除草稿，避免旧任务重新创建草稿。

超过 10 秒仍在进行的保存持续显示「结果尚未确认」，保持禁止重复提交，直到操作成功或失败。无法安全取消的 storage 写入不会触发自动重试。后台存储变化更新内存资料库，但不替换正在输入的表单控件，避免丢失焦点和光标位置。

## 验证

回归测试覆盖并发 patch、过期快照、独立模块共享锁、排队超时、慢写入、失败后继续写入，以及草稿合并、立即重复提交、失败重试、放弃草稿和保存完成后不再读取。

Chrome for Testing 153 的无头扩展验证覆盖真实键盘输入后立即保存、停止 Service Worker 后保存、页面和 Service Worker 并发写入、真实锁超时，以及持久错误提示与重试。
